## 1. Kubernetes

### What is it?
Kubernetes (K8s) is an open-source **container orchestration platform** originally developed by Google, now maintained by the CNCF. It automates the deployment, scaling, networking, and lifecycle management of containerized workloads.

### What does it do?
- Schedules containers onto available nodes based on resource requirements
- Restarts crashed containers automatically (self-healing)
- Scales applications up/down based on load (Horizontal Pod Autoscaler)
- Manages internal DNS and service discovery between pods
- Rolls out updates with zero downtime using rolling deployments
- Manages secrets, config, storage, and networking declaratively via YAML manifests

### Why use it in real environments?
Modern applications are composed of dozens of microservices that need to run reliably at scale. Without an orchestrator, teams manually manage servers, restart crashed services, and coordinate deployments — which is error-prone and impossible to scale. Kubernetes gives platform teams a **single control plane** to operate all of this consistently across dev, staging, and production.

### Real-World Example
**Netflix** runs tens of thousands of containers serving 270+ million subscribers. Kubernetes lets their platform team define the desired state of the system in YAML, and K8s continuously reconciles the actual state toward it — restarting failed pods, redistributing load on node failures, and deploying new versions with zero user impact.

In this project, Kubernetes hosts all 24 Deployments, the OpenSearch StatefulSet, 26 Services, RBAC, ConfigMaps, and Secrets — every component of the demo lives inside the `otel-demo` namespace.

## 2. Helm

### What is it?
Helm is the **package manager for Kubernetes**. It lets you define, install, and upgrade complex Kubernetes applications using reusable templates called **Charts**.

### What does it do?
- Packages multiple K8s resources (Deployments, Services, ConfigMaps, etc.) into a single distributable unit (a Chart)
- Supports parameterized configuration via `values.yaml` — one chart, many environments
- Tracks installation history and enables rollbacks (`helm rollback`)
- Manages chart dependencies (subcharts)
- Enables templating with Go templates (conditionals, loops, variables)

### Why use it in real environments?
Deploying a full application stack requires coordinating dozens of K8s manifests. Managing them as raw YAML files across multiple environments (dev/staging/prod) leads to copy-paste errors and drift. Helm solves this by separating the **template** (structure) from the **values** (configuration), so teams deploy the same chart with different settings per environment.

### Real-World Example
A SaaS company runs the same application for 50 enterprise customers, each needing isolated namespaces with custom database sizes, replica counts, and domain names. With Helm, they maintain one chart and use per-customer `values.yaml` files. Upgrading all customers to a new version is a single `helm upgrade` loop in their CI pipeline.

In this project, the `opentelemetry-demo.yaml` manifest was generated by running `make generate-kubernetes-manifests`, which rendered the OpenTelemetry Demo Helm chart along with five subcharts (Grafana, Jaeger, Prometheus, OpenSearch, OTel Collector) into a single deployable file.

## 3. OpenTelemetry (SDK + Specification)

### What is it?
OpenTelemetry (OTel) is a **vendor-neutral, CNCF-graduated observability framework**. It provides standardized APIs, SDKs, and the OTLP wire protocol to instrument applications and emit telemetry data — traces, metrics, and logs — from any language.

### What does it do?
- Provides language-specific SDKs (Java, Python, Go, .NET, Node.js, Ruby, etc.) to add instrumentation to application code
- Defines **OTLP** (OpenTelemetry Protocol) — a standard transport format for telemetry data
- Supports **automatic instrumentation** (zero-code changes via agents/bytecode injection) for common frameworks
- Captures three signal types:
  - **Traces** — end-to-end request flow across services
  - **Metrics** — quantitative measurements (latency, error rate, throughput)
  - **Logs** — structured event records

### Why use it in real environments?
Before OTel, each observability vendor (Datadog, New Relic, Dynatrace) had proprietary SDKs. Switching vendors required re-instrumenting every service. OTel decouples instrumentation from the backend — **instrument once, send anywhere**. This gives organizations freedom to change backends, use multiple tools simultaneously, and avoid vendor lock-in.

### Real-World Example
**Shopify** has hundreds of microservices in Ruby, Go, and Node.js. By adopting OTel SDKs, every service emits standardized trace and metric data. Their platform team can route that data to Jaeger for traces, Prometheus for metrics, and a log aggregator for logs — all from the same instrumentation, without modifying application code per-backend.

In this project, all 17 microservices (ad, cart, checkout, payment, etc.) are pre-instrumented with OTel SDKs in their respective languages. They all send telemetry to `http://otel-collector:4317` via OTLP gRPC.

## 4. OpenTelemetry Collector

### What is it?
The **OTel Collector** is a vendor-agnostic, high-performance **telemetry data pipeline agent**. It runs as a standalone process that receives, processes, and exports telemetry data to one or more backends.

### What does it do?
Operates through a three-stage pipeline:

| Stage | Role | Examples |
|---|---|---|
| **Receivers** | Ingest data from applications | OTLP gRPC/HTTP, Jaeger, Zipkin, Kafka |
| **Processors** | Enrich, filter, transform, batch | k8sattributes, memory_limiter, batch, transform |
| **Exporters** | Send data to backends | Jaeger, Prometheus, OpenSearch, Datadog |

Additional capabilities:
- **Connectors** — bridge pipelines (e.g., generate metrics from trace spans via `spanmetrics`)
- **Extensions** — health checks, performance profiling, zPages
- Supports multiple independent pipelines for traces, metrics, and logs simultaneously

### Why use it in real environments?
Running the collector as a central pipeline has major benefits:
- **Decoupling** — applications don't need to know which backend to send to
- **Data enrichment** — automatically adds Kubernetes metadata (pod name, namespace, node) to every span and metric
- **Tail sampling** — intelligently sample traces at the collector instead of the application
- **Fan-out** — send the same data to multiple backends simultaneously (e.g., Jaeger + Datadog + S3)
- **Protocol translation** — receive Zipkin traces, export as OTLP

### Real-World Example
An e-commerce company uses Datadog for APM but wants to also archive all raw traces to S3 for compliance. The OTel Collector sits in the middle: all services send OTLP data to the collector, which fans out to Datadog's exporter and an S3 exporter simultaneously. No application code changes.

In this project, the collector runs with 8 receivers (OTLP, Jaeger, PostgreSQL, Redis, HTTP check, Nginx, Zipkin), 6 processors (including `k8sattributes` for pod metadata enrichment), and exports to Jaeger (traces), Prometheus (metrics), and OpenSearch (logs). The `spanmetrics` connector also generates RED metrics (Rate, Errors, Duration) automatically from trace spans.

## 5. Jaeger

### What is it?
Jaeger is an open-source **distributed tracing platform** originally built by Uber, now a CNCF graduated project. It collects, stores, and visualizes distributed traces across microservices.

### What does it do?
- Receives trace data via OTLP, Jaeger Thrift, and Zipkin protocols
- Stores spans and traces (in-memory, Cassandra, Elasticsearch, or Kafka-backed)
- Provides a UI to:
  - Search traces by service, operation, duration, and tags
  - View the full call graph (flame chart) of any request
  - Compare traces across time (performance regression detection)
  - Analyze service dependency graphs

### Why use it in real environments?
In a microservices system, a single user request may touch 15 different services. When that request is slow or fails, pinpointing the root cause without distributed tracing requires sifting through logs from 15 different systems. Jaeger shows you the **exact path** the request took, how long each service took, and where it failed — in a single view.

### Real-World Example
**Uber** built Jaeger because their driver-matching system involved 100+ microservices. When a user complained "my app is slow", engineers needed to trace the request from the mobile client through API gateway → trip service → mapping service → driver service. Jaeger's flame charts made 30-minute investigations into 30-second ones.

In this project, Jaeger runs in all-in-one mode (collector + query + UI) storing up to 5,000 traces in memory. The OTel Collector forwards all traces via OTLP gRPC to Jaeger on port 4317.

## 6. Prometheus

### What is it?
Prometheus is an open-source **metrics monitoring and alerting system** originally built at SoundCloud, now a CNCF graduated project. It is the de facto standard for Kubernetes metrics.

### What does it do?
- **Scrapes** metrics from targets (HTTP `/metrics` endpoint) on a configured interval
- Stores time-series data efficiently in its built-in TSDB (Time Series Database)
- Provides **PromQL** — a powerful query language to slice and aggregate metrics
- Supports **alerting rules** that fire when conditions are met (e.g., error rate > 5%)
- Discovers scrape targets dynamically via Kubernetes service discovery
- Receives metrics via **OTLP** (push model) in addition to scraping (pull model)

### Why use it in real environments?
Prometheus answers questions like:
- "What is the p99 latency of my checkout service over the last hour?"
- "How many 5xx errors is my payment service returning per second?"
- "Is my CPU usage trending toward the limit before the next traffic spike?"

Its pull model means adding a new service is as simple as annotating its Kubernetes Service — Prometheus finds and scrapes it automatically.

### Real-World Example
**GitLab** uses Prometheus to monitor 1,000+ metrics across their SaaS infrastructure. When database connection pool exhaustion starts building, Prometheus alert rules fire PagerDuty notifications before users notice slowdowns. Their SRE team uses PromQL dashboards to correlate deployment events with latency spikes during incident investigations.

In this project, Prometheus scrapes 10+ Kubernetes-native targets (API server, nodes, cAdvisor, pods, endpoints) and also receives OTLP metrics from the OTel Collector. It retains 15 days of time-series data.

## 7. Grafana

### What is it?
Grafana is an open-source **observability and data visualization platform**. It connects to multiple data sources and renders interactive dashboards for metrics, traces, and logs.

### What does it do?
- Queries Prometheus (PromQL), Jaeger (trace search), OpenSearch (log search), and 50+ other datasources
- Renders time-series graphs, heatmaps, tables, stat panels, and geo maps
- Supports **unified dashboards** combining metrics + traces + logs in one view (correlation)
- Provides **alerting** with notification channels (Slack, PagerDuty, email, OpsGenie)
- Enables **Explore mode** for ad-hoc querying without pre-built dashboards
- **Exemplars** — links from a metric spike directly to the trace that caused it

### Why use it in real environments?
Grafana serves multiple audiences from a single platform:
- **SREs** — track SLOs, alert thresholds, and error budgets
- **Developers** — debug slow requests by jumping from a metric spike → trace → logs
- **Management** — executive-level dashboards showing system health at a glance

The key value is **correlation** — clicking a spike on a Prometheus graph can jump directly to the Jaeger trace that caused it, then to the OpenSearch log lines from that trace — all without leaving Grafana.

### Real-World Example
**The New York Times** uses Grafana to monitor their publishing infrastructure. During breaking news events, editors can watch real-time dashboards showing article page views, CDN cache hit rates, and API latency simultaneously. If the homepage response time spikes, on-call engineers open Grafana's Explore view, jump from the Prometheus latency metric to a Jaeger trace, and identify the slow database query — all within minutes.

In this project, Grafana ships with **8 pre-built dashboards** (APM, SpanMetrics, Exemplars, PostgreSQL, NGINX, OTel Collector, Linux, Demo), three configured datasources (Prometheus, Jaeger, OpenSearch), and a Grafana sidecar container that watches ConfigMaps for new dashboards dynamically.

## 8. OpenSearch

### What is it?
OpenSearch is an open-source **distributed search and analytics engine** — a community-driven fork of Elasticsearch, maintained by AWS and the OpenSearch community. It stores, indexes, and searches large volumes of structured and unstructured data.

### What does it do?
- Stores log data as indexed JSON documents
- Enables full-text search across billions of log lines in milliseconds
- Aggregates and analyzes structured log data (count errors by service, by time)
- Provides a REST API for ingestion (`PUT /index/_doc`) and search (`GET /index/_search`)
- OpenSearch Dashboards (companion UI) enables log exploration with Kibana-compatible interface
- Supports index lifecycle management (auto-delete old indices, rollover, archival)

### Why use it in real environments?
Raw logs from 20 microservices are unmanageable in flat files. OpenSearch ingests millions of log lines per second, indexes them, and makes them instantly searchable. SREs can find all 500 errors for `service=checkout` in the last 15 minutes with a single query. This replaces grepping through terabytes of log files.

### Real-World Example
**Expedia Group** processes billions of hotel search and booking logs daily. OpenSearch indexes all structured log events — failed payment attempts, search query timeouts, API errors — and correlates them. When fraud detection systems flag unusual booking patterns, analysts search OpenSearch to find all related log events across 50+ services in seconds.

In this project, OpenSearch runs as a StatefulSet with 1 replica (single-node cluster). The OTel Collector exports all application log data to OpenSearch at `http://opensearch:9200`, indexed under `otel-logs-{date}`. Grafana's OpenSearch plugin queries it for log exploration.

## 9. Apache Kafka

### What is it?
Apache Kafka is an open-source **distributed event streaming platform** built at LinkedIn. It acts as a high-throughput, durable, fault-tolerant **message bus** for event-driven architectures.

### What does it do?
- Produces and consumes ordered, immutable streams of events (messages) organized into **topics**
- Persists messages on disk for a configurable retention period (default: 7 days)
- Supports **consumer groups** — multiple consumers share the load, each reading a partition
- Scales horizontally by partitioning topics across brokers
- Guarantees at-least-once delivery (and exactly-once with proper configuration)
- Decouples producers from consumers — the producer doesn't need to know who consumes

### Why use it in real environments?
Synchronous HTTP calls between services create tight coupling — if the receiving service is down, the caller fails too. Kafka breaks this coupling: producers write events to Kafka and continue, regardless of whether consumers are running. This enables:
- **Async processing** — checkout service publishes an `OrderPlaced` event; accounting and fraud-detection consume it independently
- **Event sourcing** — replay events to rebuild system state
- **Stream processing** — real-time aggregations, transformations, and analytics

### Real-World Example
**LinkedIn** (Kafka's birthplace) processes over 7 trillion messages per day. Every profile view, connection request, and job application is an event on Kafka. The same event is consumed by the analytics team (for recommendations), the notification service (email alerts), and the feed ranking service — all independently and at their own pace.

In this project, the `checkout` service publishes `OrderPlaced` events to Kafka. The `accounting` service consumes them to record financial transactions, and the `fraud-detection` service consumes the same events to run risk analysis — both independently, without the checkout service knowing they exist.

## 10. PostgreSQL

### What is it?
PostgreSQL (Postgres) is a **powerful open-source relational database** known for its standards compliance, extensibility, and production reliability. It has been in active development for 35+ years.

### What does it do?
- Stores structured data in tables with enforced schemas and relationships
- Supports ACID transactions (Atomicity, Consistency, Isolation, Durability)
- Provides full SQL support including joins, subqueries, CTEs, and window functions
- Extensible with data types (JSON, UUID, arrays, geometric types), indexes, and stored procedures
- Supports replication (streaming, logical) for high availability
- Handles concurrent read/write workloads efficiently with MVCC

### Why use it in real environments?
Relational databases are the backbone of transactional systems — anywhere you need data integrity, relationships between entities, and complex queries. Postgres in particular is chosen over MySQL/MariaDB for its superior standards compliance, JSON support (making it a hybrid relational/document store), and advanced indexing (GIN, BRIN, partial indexes).

### Real-World Example
**Instagram** stores user account data, media metadata, and social relationships in PostgreSQL. When you follow someone, a row is inserted in a `follows` table with a foreign key constraint ensuring both users exist. A single transaction atomically updates follower counts and creates the relationship, preventing partial data states even if the server crashes mid-write.

In this project, PostgreSQL stores shipping quote data for the `quote` service. The OTel Collector's `postgresql receiver` scrapes database metrics (active connections, deadlocks, cache hit ratio, row operations) and exports them to Prometheus — visible in the PostgreSQL Grafana dashboard.

## 11. Valkey / Redis

### What is it?
Valkey is a **high-performance, open-source in-memory data store** — a community fork of Redis maintained by the Linux Foundation after Redis changed its license in 2024. It is 100% Redis-protocol compatible. Redis (Remote Dictionary Server) is used as a cache, session store, queue, and pub/sub broker.

### What does it do?
- Stores key-value pairs entirely in memory for sub-millisecond read/write latency
- Supports rich data structures: strings, hashes, lists, sets, sorted sets, bitmaps, streams
- Provides optional persistence (RDB snapshots, AOF logging)
- Supports TTL (time-to-live) for automatic key expiration
- Pub/Sub messaging for real-time notifications
- Atomic operations (INCR, LPUSH, ZADD) for safe concurrent access

### Why use it in real environments?
Databases like PostgreSQL are durable but slow for high-frequency reads. A shopping cart lookup on every page render would hammer the database. Redis sits in front as a **cache layer** — the first read fetches from Postgres and writes to Redis; all subsequent reads are served from memory in microseconds. It also serves as a **session store** (user login tokens), **rate limiter** (API throttling), and **leaderboard** (sorted sets).

### Real-World Example
**Twitter/X** uses Redis to store every user's home timeline — the 800 tweets you see when you open the app. Writing to Redis on every new tweet from followed accounts is cheap. Reading your timeline is a single Redis `LRANGE` call in under 1ms. Without Redis, loading your timeline would require joining millions of rows across multiple tables on every page load.

In this project, `valkey-cart` stores all shopping cart data keyed by `user_id`. When users add items to their cart, the cart service writes directly to Valkey. The OTel Collector's `redis receiver` scrapes Valkey metrics (connected clients, memory usage, commands per second) and exports them to Prometheus.

## 12. Envoy Proxy

### What is it?
Envoy is a **high-performance, open-source edge and service proxy** originally built by Lyft, now a CNCF graduated project. It is the data plane powering Istio, AWS App Mesh, and many API gateways.

### What does it do?
- Acts as an **L4/L7 proxy** — handles TCP, HTTP/1.1, HTTP/2, and gRPC traffic
- Routes requests based on path, header, method, and weight (traffic splitting)
- Provides **load balancing** with multiple algorithms (round-robin, least-request, ring hash)
- Terminates TLS and handles mTLS between services
- Collects rich traffic metrics (latency percentiles, request rates, error rates) out of the box
- Generates distributed traces (Zipkin/Jaeger/OTLP) for every proxied request
- Enables **circuit breaking**, **retries**, **timeouts**, and **rate limiting** declaratively

### Why use it in real environments?
Envoy externalizes cross-cutting concerns (auth, TLS, observability, retries) from application code. Instead of each microservice implementing its own retry logic and timeout handling in Go, Python, and Java, Envoy handles it uniformly at the network layer. This is the foundation of the **service mesh** pattern.

### Real-World Example
**Lyft** built Envoy because their Ruby and Python services couldn't handle the network complexity of 100+ microservices. Envoy sidecars intercept all inter-service traffic, enforcing timeouts and retries that application code never needs to implement. Every request is automatically traced and metered — their SREs get free observability without touching application code.

In this project, Envoy runs as the `frontend-proxy` — the single entry point for all traffic. It routes browser requests to the Next.js frontend, Grafana UI, Jaeger UI, and the load generator — acting as the API gateway for the entire demo application.

## 13. flagd / OpenFeature

### What is it?
**OpenFeature** is a CNCF sandbox project providing a **vendor-neutral Feature Flag API standard**. **flagd** is its reference implementation — a lightweight **feature flag evaluation daemon** that evaluates flag rules from a config file or remote provider.

### What does it do?
- Evaluates feature flags (boolean, string, number, JSON) based on rules and context
- Supports targeting rules — enable a feature for 10% of users, or only for `user_id = beta-tester`
- Provides a **gRPC and HTTP API** for flag evaluation
- Accepts flag definitions from flat files (JSON) or remote backends (LaunchDarkly, CloudBees, Flagsmith)
- Decouples feature rollout from code deployment — change behavior without redeploying

### Why use it in real environments?
Feature flags are a core **continuous delivery practice**. They allow teams to merge code to main and deploy it to production while keeping new features hidden until intentionally enabled. This decouples **deployment** (putting code in production) from **release** (showing it to users), eliminating the need for long-lived feature branches.

### Real-World Example
**GitHub** uses feature flags to roll out changes to GitHub.com. When a new code review UI is ready, it ships to production behind a flag — enabled for 1% of users first, then 10%, then 50%, with automated rollback if error rates increase. If a bug is found, the flag is disabled in seconds — no hotfix deployment required.

In this project, flagd reads flag definitions from the `flagd-config` ConfigMap. The `payment` service checks a `paymentServiceUnreachable` flag before processing payments — enabling simulated failure scenarios for observability demos without code changes.

## 14. Locust (Load Generator)

### What is it?
**Locust** is an open-source **distributed load testing framework** written in Python. It simulates concurrent users making real HTTP requests against a target application.

### What does it do?
- Simulates thousands of concurrent users performing realistic browsing flows
- Scripts user behavior in plain Python (browse products, add to cart, checkout)
- Provides a web UI to start/stop tests, configure user counts, and view real-time metrics
- Distributes load across multiple worker processes for high throughput
- Reports request rates, latency percentiles, and failure rates

### Why use it in real environments?
Without continuous traffic, observability tools have nothing to observe. In CI/CD pipelines, load generators run **performance regression tests** — if the 99th percentile latency of the checkout endpoint increases by 20% after a deployment, the pipeline fails before the change reaches production. In staging environments, load testing validates that the system handles projected peak traffic before launch.

### Real-World Example
**Stripe** runs Locust-based load tests against every major API endpoint before deploying changes to their payment processing infrastructure. Scripts simulate the exact sequence of API calls their largest customers make (create payment intent → confirm → capture). If any endpoint's p99 latency degrades past the SLO threshold during the test, the deployment is automatically blocked.

In this project, the `load-generator` service runs continuously, simulating users browsing the e-commerce store — browsing products, adding items to carts, and completing checkouts. This constant traffic populates Jaeger with traces, Prometheus with metrics, and OpenSearch with logs, making all the Grafana dashboards immediately useful on deployment.

## How All Components Work Together

```
                   User / Load Generator
                          │
                   Envoy Proxy (API Gateway)
                          │
              ┌───────────┼───────────────┐
              │           │               │
         Frontend     Business       Feature Flags
          (Next.js)    Logic          (flagd)
              │        Services           │
              └───────────┴───────────────┘
                          │ OTLP
              ┌───────────▼───────────────┐
              │    OTel Collector          │
              │  (Receive → Process →      │
              │      Export)               │
              └─────┬──────────┬──────────┘
                    │          │          │
               Traces        Metrics    Logs
                    │          │          │
                Jaeger    Prometheus  OpenSearch
                    │          │          │
                    └──────────┴──────────┘
                                │
                             Grafana
                         (Unified View)
```

Each tool solves a distinct problem, but together they form a complete **production observability platform**:

| Problem | Tool |
|---|---|
| "My app crashed" | Kubernetes restarts it automatically |
| "Which version is deployed?" | Helm tracks releases and enables rollback |
| "Why is the checkout slow?" | Jaeger trace shows the bottleneck |
| "How many errors per second?" | Prometheus metric + Grafana alert |
| "What did the service log?" | OpenSearch full-text log search |
| "Is the database healthy?" | OTel Collector PostgreSQL receiver → Grafana |
| "Which services talk to each other?" | Jaeger service dependency graph |
| "Can I release this feature safely?" | flagd gradual rollout (1% → 10% → 100%) |
| "Does my system handle peak load?" | Locust load test before release |
